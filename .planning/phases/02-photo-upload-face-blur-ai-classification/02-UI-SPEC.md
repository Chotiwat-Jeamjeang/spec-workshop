## Spacing Scale

Inherited verbatim from Phase 1 — no changes:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps |
| sm | 8px | Compact spacing — photo-slot row gap, badge padding |
| md | 16px | Default element spacing — photo-section internal gaps |
| lg | 24px | Section padding |
| xl | 32px | Layout gaps |
| 2xl | 48px | Reserved, unused this phase |
| 3xl | 64px | Reserved, unused this phase |

**New component dimension (not a spacing token):** Photo tile size = **96px × 96px**, fixed at every breakpoint (no responsive scaling — matches Phase 1's "no multi-column layout, single short form" philosophy; 96 is a multiple of 8 for grid alignment, chosen so 3 tiles + 2× 8px gaps = 304px, comfortably fitting inside the 375px viewport's 343px content width after 16px side padding).

**Exceptions (extends Phase 1's 44px minimum-touch-target rule):**
- The "+ เพิ่มรูป" add-photo tile is itself 96×96px — already exceeds 44px, no exception needed.
- The remove/change (X) control: a 14px visual glyph inside a **44px invisible circular touch-padding zone**, achieved via padding (not by enlarging the icon) — matches Phase 1's exact approach ("visually distinguished... controls, but with a larger invisible tap area").
- The "ลองใหม่" (retry) button: 44px minimum height, same class/rationale as Phase 1's `.cta`/`.location-not-this` exception.

## Color

Inherited palette, with **one new addition** justified below:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Page background (unchanged) |
| Secondary (30%) | `#F1F5F9` | Form card, empty photo-slot tile background, unclassified badge background (unchanged usage extended) |
| Accent (10%) | `#16A34A` | See "Accent reserved for" below (extended this phase) |
| Destructive | `#DC2626` | See "Destructive reserved for" below (extended this phase) |
| **Warning (new)** | `#B45309` (amber-700) | **"ควรดำเนินการ" urgency badge ONLY — nothing else** |

**Why exactly one new color, and why amber-700 not amber-600:** AI-02 requires a three-tier urgency signal (เร่งด่วน / ควรดำเนินการ / ไม่เร่งด่วน). Two of the three tiers can reuse Phase 1's existing palette with a semantically coherent extension (see below); the middle tier has no defensible existing-color match, so exactly one new color is added to complete a standard red/amber/green severity triad. **Amber-600 (`#D97706`) was rejected**: computed contrast with white badge text is 3.18:1, below WCAG AA's 4.5:1 for 14px text. **Amber-700 (`#B45309`) passes at 5.03:1.** This is the only new hex value this phase introduces.

**Accent (`#16A34A`) reserved for — Phase 1's list, PLUS two new uses:**
1. *(Phase 1, unchanged)* QR-locked location box border/badge, focus ring, "ถัดไป" primary CTA background.
2. **(new)** The "ไม่เร่งด่วน" (not urgent) urgency badge background — a deliberate traffic-light reuse (red=urgent, amber=action-needed, green=calm), not decorative. Badge text is default dark/black (contrast ≈6.4:1 on this background — **white text here fails AA at 3.30:1, so never use white text on this badge**).
3. **(new)** The "+ เพิ่มรูป" add-photo tile's icon, label text, and border — signals "the way to add more capacity," consistent with accent's confirmatory/primary-action semantic.

**Destructive (`#DC2626`) reserved for — Phase 1's list, PLUS one new use:**
1. *(Phase 1, unchanged)* Invalid/unregistered QR banner, note-length-exceeded, validate-request network failure.
2. **(new)** The "เร่งด่วน" (urgent) urgency badge background, with **white badge text** (contrast 4.83:1, passes AA). This extends destructive's meaning from "failure message" to "requires-immediate-attention severity" — both are alert-class signals; this sets the same red-for-urgent color language Phase 4's officer queue (QUEUE-02) will need to be visually consistent with later.
3. **(new)** The classify-request-failure inline caption + "ลองใหม่" retry button (D-08's genuine-failure path) and the per-photo format/size-rejection inline message — both reuse the existing `.inline-error`/`.error-banner` red treatment verbatim, no new style.

**Warning (`#B45309`) reserved for — nothing but this:**
1. The "ควรดำเนินการ" (action needed) urgency badge background, with **white badge text** (contrast 5.03:1, passes AA).

**Unclassified badge (AI-03) — deliberately NOT a colored severity badge:** background `--color-surface` (#F1F5F9), border `--color-border` (#CBD5E1), default text at `opacity: 0.7` (muted convention) — visually calm and distinct from all three urgency tiers and from the destructive error state, because AI-03 is explicitly "not an error" and must not alarm the reporter or imply a failure.

**Overlay/scrim colors (structural, not palette roles — do not add to the 5-role table):**
- Loading spinner overlay: `rgba(0, 0, 0, 0.45)` full-tile scrim, standard neutral-black-at-opacity technique.
- Remove (X) control backing: `rgba(0, 0, 0, 0.55)` circular chip behind the white X glyph, for legibility over any thumbnail.

### Slot state machine (exhaustive — five states per slot)

| State | Visual | Trigger | Next action available |
|-------|--------|---------|------------------------|
| **empty** | `.photo-slot--empty`, camera icon + "เลือกรูป" | Slot revealed but no file chosen yet | Tap tile → opens native file picker |
| **classifying** | Thumbnail + spinner overlay (D-06) | File selected, passed client-side type/size pre-check, POST in flight | None — tile is inert until response resolves |
| **classified** | Thumbnail, no overlay; caption below = waste-type text + urgency pill | 200 response, `wasteType !== 'unclassified'` | Tap thumbnail → replace (reopens file picker); tap X → remove (D-03) |
| **unclassified** | Thumbnail, no overlay; caption below = muted "ไม่สามารถระบุประเภทขยะได้", no pill | 200 response, `wasteType === 'unclassified'` (AI-03) | Same as classified — replace or remove; **no retry button** (this is not an error) |
| **error** | Thumbnail at `opacity: 0.85`; caption below = red "จำแนกไม่สำเร็จ" + "ลองใหม่" button (D-08) | Network failure or non-2xx from the classify request (genuine request failure, not an AI content outcome) | Tap "ลองใหม่" → re-POSTs the same already-selected file (no re-picking required); tap X → remove |

**Format/size rejection is NOT a sixth slot state** — a file that fails the client-side pre-check (or the server's magic-byte/size check) never transitions the slot to "filled" at all. The tile stays/resets to `empty`, and the rejection message (see Copywriting Contract) appears in `#photo-inline-error`, auto-clearing on the next valid selection for that slot.

### Zero-one-many reveal rule (D-02, locked precisely)

1. Page load: exactly one tile rendered — slot 1, `empty` state — immediately followed by the `.photo-slot--add` tile (since slot count 1 < 3 and... **no**: the add tile only appears once the *last visible slot* is non-empty; see rule 2). At page load, slot 1 is `empty`, so the add tile is **not** shown yet — matches D-02's "not three empty slots shown upfront," extended to "never more than one empty tile visible at once."
2. **Add-tile visibility rule:** `.photo-slot--add` renders immediately after the current last slot, if and only if `(rendered slot count < 3) AND (the last rendered slot is NOT in the empty state)`.
3. Tapping `.photo-slot--add` appends a new slot in the `empty` state at the next position (2 or 3) and removes the add-tile (per rule 2, it re-evaluates and disappears until that new slot is filled).
4. Reaching 3 rendered slots, all non-empty: add-tile never renders again (max reached, D-02).
5. **Removing slot 1's photo** (X control): slot 1 resets to `empty` — it never disappears, since it is the one "fixed" slot per D-02. Other slots (if any) are unaffected; the add-tile re-evaluates per rule 2 (likely hides again, since slot 1 is now empty and — if slot 1 is the last slot — rule 2's condition fails).
6. **Removing slot 2 or 3's photo** (X control): that slot is removed from the DOM entirely (collapses), not reset to empty — it was optionally revealed, so removing its content also removes its capacity, and the add-tile re-appears per rule 2.

### CTA gating (D-04)

The "ถัดไป" button's disabled/blocked logic (client-side; server-side mirror is a `plan-phase` concern, not this contract's) has two independent conditions, each with its own `#photo-inline-error` message:

1. **Zero photos attached** (no slot has ever reached `classifying`/`classified`/`unclassified`/`error` — i.e., all slots are `empty`): blocked, message "กรุณาแนบรูปภาพอย่างน้อย 1 รูป".
2. **≥1 slot still `classifying`**: blocked, message "กรุณารอผลการประมวลผลให้เสร็จสิ้น".

A slot in the `error` state still counts as "attached" for condition 1 (the file selection happened; only the classify request failed) — the CTA is not blocked by a slot being in `error`, only by zero attachment or in-flight requests. This matches AI-03/D-08's framing that neither "unclassified" nor "a failed classify request" should hard-block the reporter's ability to proceed with the form (the phase boundary explicitly excludes report *persistence* — Phase 3's job).
