## Photo attach flow

### Q1: การแนบรูปควรอยู่ตรงไหนใน flow?

| Option | Description | Selected |
|--------|-------------|----------|
| หน้าเดียวกัน | เพิ่มช่องแนบรูปเข้าไปในฟอร์มเดิม ระหว่าง note กับปุ่ม "ถัดไป" — เรียบง่ายที่สุด ไม่ต้องเปลี่ยน routing | ✓ |
| แยกเป็นขั้นที่ 2 | กด "ถัดไป" จากหน้าสถานที่/note แล้วเข้าหน้าแนบรูปโดยเฉพาะ — เหมือน wizard หลายขั้นตอน | |

**User's choice:** หน้าเดียวกัน (แนะนำ)

### Q2: ช่องแนบรูปควรแสดงกี่ช่อง และเพิ่มทีละรูปหรือเลือกหลายรูปพร้อมกัน?

| Option | Description | Selected |
|--------|-------------|----------|
| 1 ช่องคงที่ + ปุ่ม "+ เพิ่มรูป" | เริ่มต้นเห็นช่องเดียว กดเพิ่มค่อยโผล่ช่องถัดไป สูงสุด 3 | ✓ |
| แสดง 3 ช่องว่างตั้งแต่แรก | เห็นชัดว่าแนบได้สูงสุด 3 รูปทันที แต่กินพื้นที่จอมากกว่าเมื่อมีแค่ 1-2 รูป | |

**User's choice:** 1 ช่องคงที่ + ปุ่ม "+ เพิ่มรูป" (สูงสุด 3)

### Q3: หลังเลือกรูปแล้ว ผู้ใช้ควรลบ/เปลี่ยนรูปนั้นได้ไหมก่อน submit?

| Option | Description | Selected |
|--------|-------------|----------|
| ลบ/เปลี่ยนได้ | แต่ละช่องที่แนบแล้วมีปุ่ม X เพื่อลบหรือเลือกไฟล์ใหม่แทน | ✓ |
| ลบได้อย่างเดียว ต้องแนบใหม่หากจะเปลี่ยน | ง่ายกว่าใน implement แต่ UX ด้อยกว่า | |

**User's choice:** ลบ/เปลี่ยนได้ (แนะนำ)

### Q4: ปุ่ม "ถัดไป" ควรบล็อกการกดหากยังไม่แนบรูปเลยไหม?

| Option | Description | Selected |
|--------|-------------|----------|
| บล็อก ต้องมีอย่างน้อย 1 รูปจึงกดต่อได้ | ตรงกับ SPEC edge case "ไม่ได้แนบรูปภาพ → ปฏิเสธการ submit" — เช็คทั้ง client และ server | ✓ |
| ยังไม่บังคับ เก็บเป็น Phase 3 | Phase 2 ทำแค่ upload/classify ส่วนบังคับว่าต้องมีอย่างน้อย 1 รูปค่อยทำตอน submit จริงใน Phase 3 | |

**User's choice:** บล็อก ต้องมีอย่างน้อย 1 รูปจึงกดต่อได้ (แนะนำ)

## Upload/classify UX timing

### Q1: เมื่อผู้ใช้เลือกรูปซักรูป ควรส่งไปจำแนกเมื่อไหร่?

| Option | Description | Selected |
|--------|-------------|----------|
| ส่งทันทีหลังเลือกไฟล์ | แต่ละช่องส่งอัปโหลด+จำแนกทันทีที่เลือก เห็นผลเร็วทีละรูป ตรงกับ AI-01 | ✓ |
| รอกดปุ่มตรวจสอบทีเดียว | เลือกรูปครบแล้วกด "ตรวจสอบ" ทีเดียว ส่งทุกรูปพร้อมกัน | |

**User's choice:** ส่งทันทีหลังเลือกไฟล์ (แนะนำ)

### Q2: ระหว่างรอผล AI ควรเห็นอะไรที่ช่องรูปนั้น?

| Option | Description | Selected |
|--------|-------------|----------|
| เทียบรูป + spinner ทับ | เห็น thumbnail รูปที่เลือกทันที พร้อม spinner/overlay จนกว่า AI จะตอบกลับ | ✓ |
| ข้อความ "กำลังตรวจสอบ..." เท่านั้น ไม่เห็นรูป | เรียบง่ายกว่า แต่ผู้ใช้ไม่เห็นภาพที่เลือกจนกว่าจะเสร็จ | |

**User's choice:** เทียบรูป + spinner ทับ (แนะนำ)

### Q3: ผลจำแนกของ AI ที่แสดงให้ผู้แจ้งเห็น ควรแก้ไข/เลือกเองได้ไหม ก่อนกด submit?

| Option | Description | Selected |
|--------|-------------|----------|
| แสดงเฉยๆ แก้ไขไม่ได้ใน Phase นี้ | ผู้แจ้งเห็นผล AI เป็นข้อมูลเฉยๆ ส่วนการแก้ไขเป็นหน้าที่เจ้าหน้าที่ (Phase 4 officer queue) ตรงกับ AI Ethics constraint ใน PROJECT.md | ✓ |
| ให้ผู้แจ้งแก้ประเภทขยะได้เองที่หน้านี้ | เพิ่ม UI แก้ไขเพิ่มเติม | |

**User's choice:** แสดงเฉยๆ แก้ไขไม่ได้ใน Phase นี้ (แนะนำ)

### Q4: ถ้าการส่งรูปไปจำแนกล้มเหลว (network/server error) ควรทำอย่างไร?

| Option | Description | Selected |
|--------|-------------|----------|
| แสดง error + ปุ่ม "ลองใหม่" ที่ช่องนั้น | เหมือน pattern ของ validate-banner ใน Phase 1 (เก็บข้อมูลที่กรอกไว้เสมอ ไม่หาย) — ผู้ใช้กดลองใหม่ได้ทันที ไม่ต้องเลือกไฟล์ใหม่ | ✓ |
| ถือเป็น unclassified เงียบๆ เหมือน AI จำแนกไม่ได้ | ง่ายกว่า แต่ผู้ใช้ไม่รู้ว่าเกิด network error จริงๆ หรือ AI จำแนกไม่ได้จริงๆ | |

**User's choice:** แสดง error + ปุ่ม "ลองใหม่" ที่ช่องนั้น (แนะนำ)

## Claude's Discretion

- **Face-blur implementation approach** — ไม่ได้ถูกเลือกมาคุยในรอบนี้ ปล่อยให้ research/planning ยืนยันแนวทางตามที่ `.claude/CLAUDE.md` แนะนำ (ต่อยอด Claude Vision call เดิมให้คืน face bounding box มาด้วย แล้วเบลอด้วย `sharp`) พร้อมกำหนดรายละเอียด (ความแรงของการเบลอ, ต้องไม่เก็บไฟล์ต้นฉบับที่ยังไม่เบลอไว้เลย)
- **Multi-photo urgency aggregation** — ไม่ได้ถูกเลือกมาคุยเช่นกัน SPEC ไม่ได้ระบุว่าเมื่อมีหลายรูป (สูงสุด 3) จะรวมค่า coverage_percentage ของแต่ละรูปเป็นความเร่งด่วนระดับรายการเดียวอย่างไร ปล่อยให้ planning ตัดสินใจโดยอ้างอิงจาก `deriveUrgency()` ที่มีอยู่แล้วใน `wasteImageClassifier.js`
