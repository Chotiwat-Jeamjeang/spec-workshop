<objective>
Close the loop with a real server round trip: a validate endpoint that independently re-checks the location and the note length, and a CTA that drives it with proper loading, inline-error and failure states.

Purpose: until now every SUBM-02 and SUBM-03 guarantee lives in a `GET` render or a browser attribute, both of which a client can bypass. This plan gives both requirements genuine server-side enforcement and makes the Walking Skeleton's "one real UI interaction wired to the API" concrete.
Output: `POST /api/waste-reports/validate` and the CTA that calls it.
</objective>

## Planner decision recorded

`01-RESEARCH.md` Open Question #1 asked whether Phase 1 needs any `POST` endpoint at all, given that persistence is explicitly Phase 3's job. Resolved as **Option B: build the narrow validate endpoint**, for three reasons: `01-UI-SPEC.md`'s Copywriting Contract already specifies a CTA loading state (`กำลังตรวจสอบ...`) and a validate-failure banner, which presuppose a server round trip; SUBM-02 and SUBM-03 otherwise have no enforcement a curl request cannot walk straight past; and the Walking Skeleton contract requires one real UI interaction wired to the API. The endpoint validates and returns a verdict — it writes nothing, mints no id, and stores nothing. Rated `reversible`: it is one handler behind a stable JSON contract, and Phase 3 either extends it into a persisting submit or leaves it as a cheap pre-check ahead of Phase 2's expensive multipart upload.

Add `POST /api/waste-reports/validate` to `src/routes/report.js`, following `classify.js`'s handler shape: validate in order, early-`return res.status(400).json({ error: '<Thai message>' })` on the first failing check, and respond with the success verdict otherwise.

The validation order and rules:

1. Read `location_id`, `sig` and `note` from `req.body`. Treat a non-string `location_id` exactly as an absent one.
2. If `location_id` is absent or empty, respond 400 with `กรุณาเลือกจุดที่แจ้ง` — the same copy the client shows inline, so a bypassing client gets the same answer as the UI.
3. Look the id up with `locationStore.findById`. If it is not registered, respond 400 with `ไม่พบจุดนี้ในระบบ กรุณาติดต่อเจ้าหน้าที่`.
4. If a `sig` was supplied, it must verify: re-run `verifyLocationSignature(location_id, sig)` and respond 400 with that same message when it fails. Re-run it here rather than trusting anything about an earlier request — a prior successful `GET /report` is a different request entirely, and "the page rendered the locked state" is not a fact this handler can observe. A submission with no `sig` at all is the dropdown path and is judged on registry membership alone, consistent with the two structurally separate trust levels established in 01-02.
5. If `note` is present, it must be a string of at most 500 code units measured with the value's `length` property; otherwise respond 400 with `รายละเอียดยาวเกินไป (ไม่เกิน 500 ตัวอักษร)`. Do not measure this in bytes: Thai averages three UTF-8 bytes per code point, so a byte-derived limit would reject a valid Thai note at roughly 166 characters while the browser's own `maxlength` accepted 500 — the server and the client must count the same way or the counter lies to the user. An absent, null, or empty `note` passes; it is optional.
6. On success respond 200 with a JSON verdict carrying a boolean valid flag and the resolved location's `location_id` and `name` — enough for the client to render a confirmation, and nothing more. Do not include `lat`/`lng`.

This handler writes nothing. It must not create, append to, or read `waste-reports.json`, must not mint a report id, and must not touch the filesystem at all — persistence is Phase 3 (STORE-01) and is explicitly outside this phase's boundary. It must also not rate-limit or dedup: that is Phase 6.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/waste-reports/validate` | Fully untrusted, unauthenticated JSON body. `location_id`, `sig` and `note` are all attacker-controlled and reach this endpoint whether or not any page was ever rendered. |
| server verdict → client banner | Server-supplied strings are written into the DOM by the client script. |
| request body → JSON parser | An unbounded body would be parsed before any handler validation runs. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-19 | Spoofing | `POST` path trusting a prior successful `GET` | high | mitigate | The handler re-runs `verifyLocationSignature` and `findById` on the submitted values; it observes nothing about earlier requests and holds no session. Enforced by a source assertion that the signature check appears on the POST path as well as the GET path. |
| T-01-20 | Tampering | client-side-only note limit bypassed by curl or devtools | high | mitigate | Server-side length re-check in UTF-16 code units, matching the browser's own `maxlength` measure exactly, with the byte-based measure banned by a source assertion so the two can never silently diverge. |
| T-01-21 | Tampering (script injection) | server error string rendered into the banner | high | mitigate | The client assigns every message through `textContent`; `innerHTML` is banned by a source assertion, so no server or attacker-influenced string is ever parsed as markup. |
| T-01-04 | Information Disclosure | validate-endpoint failure messages | medium | mitigate | The QR-failure branch reuses the same single generic message as the GET path — unknown id and bad signature are indistinguishable to a caller. The distinct note-length and missing-location messages are safe to differentiate: neither reveals anything about the signing scheme. |
| T-01-22 | Denial of Service | unbounded JSON request body | medium | mitigate | `express.json({ limit })` set explicitly to a small ceiling, so oversized bodies are rejected by the parser before any handler work. |
| T-01-10 | Information Disclosure | verdict response payload | medium | mitigate | The success verdict returns only the valid flag plus the resolved `location_id` and `name`; `lat`/`lng` are excluded, matching the `GET /api/locations` projection. |
| T-01-05 | Denial of Service | unauthenticated submission endpoint (spam, volume) | medium | accept | Rate limiting and dedup are Phase 6 (ABUSE-01/ABUSE-02) per `01-CONTEXT.md`'s Phase Boundary. Recorded as an accepted, phase-scoped risk; the endpoint's zero-persistence design bounds the blast radius in the meantime, since a flood creates no stored records. |
</threat_model>
